# Verify a report's load-bearing claims yourself — and check your own grep before trusting it

**Problem** — An 11-agent feature inventory of this repo produced the claims a whole review would rest on ("no data is shared between accounts", "no notifications exist", "delegation is a label"). Acting on a subagent's summary for a conclusion that important is not safe, and one agent's aside mentioned a possible bug nobody had confirmed.

**Approach** — Each load-bearing claim was reduced to a single grep with a binary answer, run directly: `household_id` across `src/` and `supabase/` (2 hits, neither on a data table), `new Notification(|pushManager|web-push|cron` (zero), `events.insert|update|delete|patch` on the Google client (zero, so read-only), `webcal|ics_url` (zero). Each took seconds and settled a claim the review would otherwise have asserted on trust. Chasing the flagged aside the same way found a real defect: the AI writes calendar rows with `source='manual'`, the only reader filters `.eq('source','uploaded_calendar')`, and the chat context re-reads the table *unfiltered*, so the assistant insists an invisible event exists. Two of my own greps were also wrong — one missed a UI call site because it searched only `.tsx` for a literal path when the caller went through a hook, and one missed lowercase `create table` because it was case-sensitive. Both would have put a false claim in the document.

**Solution** — `docs/competitive-review.md` §4b documents three defects found this way; a ground-truth file recorded each verified claim with the command that settled it.

**Rule** — Before publishing a conclusion that rests on a subagent's report, restate each load-bearing claim as one narrow grep you run yourself, and write the command and its result down next to the claim. Prefer absence-proving greps (`grep -rn <symbol> src | wc -l`) because they are cheap and unambiguous. When a grep returns zero or a suspiciously round answer, vary it before believing it — add `-i`, search a wider file set, and follow the hook or re-export rather than the literal path. A negative result from a too-narrow pattern is indistinguishable from a true absence. When an agent flags something in passing as odd, trace it to the reader as well as the writer: a write path that looks correct in isolation is still broken if nothing queries what it wrote.

**Dead ends** — Trusting a single case-sensitive grep over a SQL corpus that mixes `CREATE TABLE` and `create table`. Concluding "no UI call site" from grepping `.tsx` files for an API path when the call goes through a hook in `.ts` — grep for the hook name too. Counting registry keys with a regex over a JSX file and getting a number inflated by unrelated object literals; intersect two extracted id lists with `comm` instead.
