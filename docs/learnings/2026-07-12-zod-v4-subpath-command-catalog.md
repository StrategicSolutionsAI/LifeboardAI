# "Blocked on the next major version" — check for a subpath export first

**Problem** — The chat command catalog lived in four lockstep copies (TS union in chat-commands.ts, zod union in validations.ts, REALTIME_TOOLS JSON Schema, hand-written prompt text); unification was twice deferred as "needs a zod v4 toJSONSchema migration, too large for a cleanup pass."

**Approach** — Checked whether the blocker was real before scheduling a migration: zod 3.25+ ships the entire v4 API as a `zod/v4` subpath export alongside classic v3. `node -e "require('zod/v4').z.toJSONSchema(...)"` confirmed it works in the installed 3.25.76 — the "migration" was never needed. Built `src/lib/chat-command-catalog.ts` on zod/v4 (each command = name + description + mutates flag + params schema with `.describe()` per field) and derived everything from it: `executeCommandSchema` (validation), `LifeboardCommand` (z.infer), `REALTIME_TOOLS` (z.toJSONSchema, `$schema` key stripped), `isMutatingAction`. The prompt in getCommandsPrompt stays hand-written (its wording is prompt engineering) with a lockstep test instead.

**Solution** — New catalog module + 7-test lockstep suite (`src/lib/__tests__/chat-command-catalog.test.ts`); validations.ts and api-utils.ts bridge v3/v4 with a minimal structural `BodySchema<T>` interface (`safeParse` only) since classic `z.ZodType` doesn't type-match v4 schemas. Verified with a field-by-field diff of generated vs old REALTIME_TOOLS: names/descriptions/required identical, only additive constraints (minLength/maxLength/pattern the validator already enforced, plus additionalProperties:false).

**Rule** — When work is deferred as "blocked on the next major version of a library", verify the blocker with one `node -e` probe before believing it — libraries increasingly ship the next major as a subpath export of the current one (zod/v4 inside zod 3.25+). When mixing zod v3 and v4 in one codebase: shared helpers must use `error.issues` (exists in both; `.errors` is v3-only) and accept schemas via a structural interface, not `z.ZodType`. When replacing hand-written derived artifacts (JSON Schema, prompts) with generated ones, diff old vs new field-by-field and review every delta deliberately — "tests pass" doesn't show you what the model/API now receives.

**Dead ends** — Upgrading the whole repo to zod v4 (touches every route's error-message format for nothing); generating the typed-chat prompt from the catalog (its example-JSON wording is tuned prompt content — a lockstep test protects it more safely than generation); spreading `matchAll` in the test (needs downlevelIteration at this tsconfig target — use an exec loop).
