# "Add feature X" when X already exists but the picker hides it

**Problem** — Asked to "add a period tracking widget". The user believed none existed; searching "period" in the widget library showed "No widgets found matching your criteria".

**Approach** — Before writing any widget code, grep the repo for the domain word and its synonyms (`grep -rn "cycle" -il`). That immediately surfaced a complete feature: `supabase/migrations/20260305_add_cycle_tracking_table.sql`, `src/app/api/widgets/cycle-tracking/route.ts`, `src/features/widgets/components/cycle-tracking-widget.tsx`, plus entries in the card registry, modal registry, and `widget-templates.ts`. So the bug was discoverability, not absence. Then reproduce the user's actual failure in the browser rather than reasoning about it: an authed Playwright session, open Add Widget from the Health bucket, type "period", screenshot. That screenshot showed the empty-state and, critically, that a category chip ("Health") was pre-selected — the second cause, which reading the filter code alone would have under-weighted. Last, confirm the pre-existing feature isn't broken for a different reason: query `cycle_tracking` with the service-role client to prove the migration reached the live DB (schema drift is the top failure mode in this repo).

**Solution** — Two independent causes, both in the search path:
1. `src/lib/widget-templates.ts` — template was `name: "Cycle Tracker"` / `description: "…menstrual cycle…"`. The library only searches `name` and `description`, so the word users type ("period") matched nothing. Renamed to `"Period & Cycle Tracker"` and put "period flow" in the description. Matching title in `src/features/widgets/widget-modal-registry.ts`.
2. `src/features/widgets/components/widget-library.tsx` — the bucket-recommended category chip was ANDed with the search term, and the tracker's category is `medical`, so a search from the Health bucket could never return it at any wording. Typing a query now does `setSelectedCategory('all')` in the input's `onChange`.

**Rule** — When asked to add a feature, grep for the domain concept and its synonyms before designing anything; a "missing" feature in a mature repo is more often unreachable than absent. When a picker/library has both a text search and a category (or tag) filter, never AND them silently — a query must span the whole catalog, or the UI reports "nothing exists" about something that does. Prefer resetting the visible filter to "All" over letting the filter apply invisibly, so the chip state never disagrees with the result list. Also: a user-facing name is a search key, so it must contain the word users actually type, not only the clinical term.

**Dead ends** — Building a second, "period"-named widget alongside the cycle tracker (would have duplicated a table, an API route, and 960 lines of component). Fixing only the wording — verified insufficient, because the category filter still excluded it. Assuming `prefers-color-scheme` in Playwright would exercise dark mode here; the app themes from a stored user preference, so `colorScheme: 'dark'` rendered light and proves nothing about dark parity.
